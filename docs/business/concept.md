# hikidashi コンセプト

複数案件で並行して走らせている Claude Code での仕事を管理する、手元の秘書のようなローカルツール。
頼めば案件を「引き出し」として登録して作業場所を用意し、
いま何が動いていて、次に誰が何をすべきかを尋ねればすぐ答える。

仕組みの設計は [`../development/architecture.md`](../development/architecture.md) が持つ。

## 解決したい課題

案件をまたいで Claude Code を並行で動かしていると、どの作業がオープンで、
どれが自分の入力待ちかを追いきれなくなる。感覚としては「机の上が散らかって整理できていない状態」に近い。

hikidashi は、秘書として案件ごとの引き出しを用意して片付け、開ければ中身と状態がすぐわかる状態にすることを目指す。

## 基本の考え方

- 案件（原則 1 案件 = 1 リポジトリ）をひとつの **引き出し** として扱う
- 引き出しは人が明示的に **登録** したときだけ作る。未登録のリポジトリで Claude Code が動いても記録しない
  - 単発の小さな作業まで記録されると、引き出しが散らかるため
- 登録すると、引き出しのデータと、その案件用の tmux セッション（1 案件 = 1 tmux セッション）を用意する。
  Claude Code はその tmux セッションの window / pane で動かす
- 引き出しの中には、人間が書く **備忘録** と、その案件で開いている **Claude Code セッション** が入っている
- 各セッションは tmux の pane と紐づき、一覧から選べばその pane にすぐ飛べる
- 秘書は案件の状況を尋ねられると、登録済みの全案件の概況（Open な Issue の件数・セッションの状態など）を答え、
  案件を指定されればその詳細（セッションごとの状態と次アクション、備忘録）を答える
- 状態の記録・次アクションの抽出・入力待ちの件数表示は、秘書が状況を知るための目と耳にあたる
- 登録・状況の確認は `hikidashi` のコマンドが実体で、Claude Code の plugin の skill から自然な言葉で頼める
  （例: 「この案件を登録しといて」）

## 語彙

| 用語 | 識別子 | 意味 |
| --- | --- | --- |
| 引き出し | `drawer` | 案件（リポジトリ） |
| 中身 | `notes.md` | 案件の備忘録 |
| 登録する | `add` | 作業ディレクトリの案件を引き出しとして登録し、tmux セッションを用意する操作（`hikidashi add`） |
| 並べる | `list` | 全案件の概況を 1 案件 1 行で出す操作（`hikidashi list`） |
| 見る | `show` | 指定した案件（省略時は作業ディレクトリの案件）の詳細を出す操作（`hikidashi show [<案件>]`） |
| 外す | `remove` | 誤登録や終わった案件の登録を取り消す操作（`hikidashi remove`） |
| 開ける | `open` | 一覧から引き出しを選び、セッションの pane に移動する操作（`hikidashi open`） |

コード・データ・コマンドでは識別子の列の語だけを使い、同じ概念に別の名前（`case`・`project` 等）を与えない。

コマンドの短縮エイリアスとして `hd` / `hiki` を用意する想定。

## 周辺プロダクトとの関係

| プロダクト | 役割 |
| --- | --- |
| fukan | GitHub Issue を起点に AI へタスクを振り、全体を俯瞰する |
| moira | 割り当てと状態管理（決定論部分） |
| **hikidashi** | 人間が手元で並走させている案件とセッションを、秘書として管理して捌く |

役割が異なるため共存できる。将来的には、hikidashi の状態記録の形式が、
fukan の Worker が状態を報告する際の仕様の叩き台にもなり得る。
